# bbb-mp4-simple

Разовый запуск оригинального образа [manishkatyan/bbb-mp4](https://github.com/manishkatyan/bbb-mp4) с готовым URL записи BigBlueButton 2.3. Chrome в контейнере открывает переданный URL напрямую; адрес BBB из имени домена и ID не собирается. VM с Docker и сервер BBB могут находиться на разных машинах, но контейнеру необходим сетевой доступ к URL и связанным ресурсам записи.

## Установка на Ubuntu VM

Docker уже должен быть установлен; пользователь, запускающий команды, должен иметь право пользоваться Docker. Нужны Python 3 и systemd (стандартные компоненты Ubuntu), а для установки systemd-сервиса — root или sudo. Выполните после создания VM:

```bash
curl -fsSL https://raw.githubusercontent.com/vsesem-git/bbb-mp4-simple/main/deploy.sh -o deploy.sh
bash deploy.sh
cd ~/bbb-mp4-simple
```

Ссылка выше работает после публикации изменений в `main`. Также можно сначала клонировать нужную ветку репозитория и запустить `./deploy.sh` из неё. Скрипт подготовит каталог `recordings`, создаст `.env` с абсолютным путём `COPY_TO_LOCATION`, закрепит текущий оригинальный Docker-образ по digest (или скачает его при первой установке) и установит и запустит systemd-сервис `bbb-mp4-web`. Он будет автоматически запускаться после перезагрузки VM от имени пользователя, выполнившего развёртывание.

Повторный запуск сохраняет существующий `.env` и файлы, не обновляет checkout и использует тот же digest образа, но **перезапускает веб-сервис**. Новая версия не позволит развёртывать её во время активной конвертации: очередь ставится на паузу перед перезапуском. При переходе со старой версии дождитесь окончания и очереди, и текущей конвертации; до завершения обновления не добавляйте задания. Если нужен другой каталог результатов, измените `COPY_TO_LOCATION` в `.env` (это shell-файл, путь с пробелами нужно заключить в кавычки) и повторите `./deploy.sh`.

## Веб-интерфейс

Откройте в браузере `http://<IP-VM>:8080` с компьютера в доверенной сети. Вставьте полный playback URL и нажмите «Добавить задание». Таблица показывает очередь, этап (подготовка, запись, финализация, проверка), приблизительный прогресс и оставшееся время, а также размер и длительность готового файла. Доступны поиск по ID или ссылке и фильтр по статусу. По нажатию на превью скриншот открывается крупно; кнопка «Журнал» показывает последние сообщения задания. Обычные задания выполняются по одному в порядке добавления. Для ожидающего задания кнопка «Принудительно» запускает его параллельно с текущими, не останавливая их. Всего допускается **не более трёх** активных заданий, включая обычное и проверку MP4; при занятых трёх слотах запуск недоступен. Освобождение дополнительного слота само по себе не запускает другие обычные задания параллельно. Параллельная работа увеличивает нагрузку на CPU, память, сеть и диск. Превью снимается внутри контейнера при появлении изображения и затем примерно раз в минуту. Если скриншот пока недоступен, отображается прочерк.

У каждого задания отдельные контейнер, журнал и превью: в очереди задание можно убрать, выполняющееся — остановить, не прерывая остальные. После остановки можно удалить запись из списка. У готового задания доступны скачивание, удаление и пересоздание. **Удаление удаляет и соответствующий MP4 с диска**; перед удалением потребуется подтверждение. **При пересоздании прежний MP4 удаляется сразу после подтверждения**, ещё до запуска. Если новое задание завершится ошибкой или будет остановлено, прежний файл не восстановится. Не запускайте одновременно обработку одной записи вручную через `convert.sh` и через веб-интерфейс.

Задания, ссылки и последнее превью сохраняются в `state/` на VM. Этот каталог может содержать URL с токенами и доступен только пользователю сервиса. Настройки и последние 16 000 символов журнала каждого задания также сохраняются там; журналы могут содержать данные записи. Если Chrome/FFmpeg аварийно завершились или полученный файл не прошёл проверку, выполняются до двух автоматических повторов (три попытки всего) с задержками 5 и 10 секунд. Явно обнаруженная отсутствующая запись, неподходящий кодек/разрешение и ошибки инфраструктуры Docker повторно не запускаются. Ожидание повтора можно остановить; параметры и принудительный режим сохраняются при повторах и перезапуске сервиса. Кнопка «Принудительно» у ожидающего повтора также отменяет оставшуюся задержку, если есть свободный слот. При явном пересоздании задание снова становится обычным. После перезапуска ожидающие задания продолжат выполняться; прерванное задание автоматически начнётся заново с сохранёнными настройками (не более двух таких перезапусков). Если до сбоя уже появился готовый или промежуточный MP4, сервис сначала проверит его и при успехе восстановит без повторной записи. Явно останавливавшееся задание не запускается автоматически. При первом запуске этой версии уже имеющиеся в каталоге результатов MP4 появятся в списке. Поскольку прежняя версия не сохраняла URL, для пересоздания таких файлов нужно заново вставить playback URL в форму.

### Если длительность не определяется

BBB иногда показывает плеер раньше, чем медиа возвращает длительность (`NaN`). Конвертер ждёт её до 120 секунд и больше не передаёт `NaN` в FFmpeg. Если метаданные так и не появились, откройте у задания **«С длительностью…»** и введите полную длительность как `3:04:25` (или целое число секунд). Для нового задания то же поле находится в дополнительных параметрах. Вручную заданная длительность сохраняется при пересоздании; до 7 суток. Время с минусом в плеере — *оставшееся* время: используйте его как полную длительность только если воспроизведение находится в самом начале. Неверное значение может обрезать запись или добавить лишнее время; проверка сравнит результат именно с введённым числом, а не с независимо установленной длительностью.

При запуске из командной строки можно передать, например, `BBB_MP4_DURATION=11065 ./convert.sh "<playback-url>"`. В остальных случаях длительность определяется автоматически. Chrome продолжает открывать переданный URL напрямую.

### Обновление образа

При первом обновлении `deploy.sh` сохраняет digest уже установленного `manishkatyan/bbb-mp4:latest` в `state/image.ref`. Если образ ещё не скачан, сначала скачивается `latest`. Последующие обычные запуски используют закреплённый digest и не обновляют версию незаметно. После проверки совместимости можно явно обновить образ командой `./deploy.sh --update-image` в отсутствие активной конвертации. Если понадобится вернуться к прежнему digest, сохраните его заранее и замените строку `state/image.ref` на валидную ссылку вида `manishkatyan/bbb-mp4@sha256:…`, затем запустите `./deploy.sh`. Закрепление не доказывает, что образ проверен для каждой записи или режима H.265.

### Настройки конвертации

В разделе «Глобальные настройки конвертации» выбираются кодек, разрешение, битрейт видео и аудио, частота кадров (FPS) и пресет. Для новой установки значения по умолчанию: **H.264, 1280×800, видео auto, аудио 128 кбит/с, 30 FPS, medium**. В режиме auto используются H.264 CRF 22 или H.265 CRF 26. Второй режим — H.265; он обычно требует больше процессорного времени и поддерживается не всеми устройствами и браузерами. Кодировщик H.265 не ограничивается двумя рабочими потоками; при параллельных заданиях он может существенно загрузить CPU и память.

Доступные размеры: **1280×800**, **1920×1080 Full HD**, **2560×1440 QHD (2K)**, **2560×1080 UltraWide Full HD** и **3440×1440 UltraWide QHD (2K)**. Два последних обычно обозначают как 21:9. Для заданий с настройками Chrome, экран Xvfb, захват FFmpeg и итоговый MP4 используют выбранный размер, без промежуточного увеличения 1280×800. Сам плеер BBB и медиа могут адаптировать расположение и добавлять поля в зависимости от исходного материала. Более высокий размер не восстанавливает детали, отсутствующие в источнике, и значительно повышает нагрузку и расход памяти.

Для видео доступны auto (CRF), 1000, 1500, 2000, 2500, 4000, 6000, 8000, 12000, 16000, 20000 и 30000 кбит/с; для аудио — 64, 96, 128, 160, 192, 256, 320 и 512 кбит/с. Выберите «Другое значение», чтобы задать другое целое число: для видео 250–50000, для аудио 32–512 кбит/с. Битрейт — приблизительная скорость данных: выше обычно даёт более крупный файл и может сохранить больше деталей/качества звука, но не улучшит исходный материал. При заданном битрейте можно грубо оценить размер: `(видео + аудио) × секунды / 8` килобайт плюс накладные расходы; в режиме auto размер заранее не фиксирован.

Частота кадров задаёт частоту захвата экрана: **15, 24, 25, 30, 50 или 60 FPS**. Меньше кадров — ниже нагрузка и менее плавное движение; больше кадров — более плавное движение, но 50–60 FPS, особенно с H.265 и большим разрешением, могут перегрузить VM. Высокий FPS не создаёт новые кадры в исходном видео. На слишком слабой VM запись может пропускать кадры или не завершиться; сначала проверьте короткую запись с выбранными настройками.

**Пресет** управляет компромиссом скорости/нагрузки и эффективности сжатия кодировщика: `ultrafast` — наименьшая нагрузка и обычно менее эффективное сжатие; `superfast`, `veryfast`, `faster`, `fast` — промежуточные варианты; `medium` — баланс; `slow` — больше вычислений. При CRF более медленный пресет часто даёт меньший файл при сопоставимом качестве; при заданном битрейте может дать лучшее качество при похожем размере. Это не гарантируется для каждой записи. Запись экрана идёт в реальном времени: выбор быстрого пресета сам по себе не сокращает продолжительность записи, но помогает VM успевать.

Для отдельного нового задания можно переопределить любое значение в форме добавления; «Глобальное значение» использует сохранённое. Настройки фиксируются при создании: изменения глобальных значений не влияют на уже созданные задания или их пересоздание. Существующие глобальные настройки и задания сохраняются, а в старых настройках без FPS используется прежнее значение **30 FPS**. Ранее сохранённые низкие разрешения продолжают работать у существующих заданий и глобальных настроек, но больше не доступны как новый выбор; после изменения глобального разрешения вернуться к низкому через интерфейс нельзя. Если ранее сохранялся числовой битрейт (например, 2500 кбит/с), он сохраняется; переключите его на `auto` вручную, чтобы использовать CRF. Обычный вызов `convert.sh` без параметров веб-задания использует настройки оригинального образа.

H.265 и более медленный пресет часто уменьшают размер, но **меньший размер и полное отсутствие потери качества одновременно гарантировать нельзя**: CRF — сжатие с потерями, а результат зависит от записи. Значения CRF разных кодеков не равнозначны; H.265 CRF 26 может отличаться по качеству от H.264 CRF 22. Сравните качество и размер на ваших записях; если важнее качество и совместимость, используйте H.264 и исходное разрешение.

### Проверка и диагностика

После записи проверяются формат, длительность, наличие видео- и аудиодорожки, разрешение и кодек, затем видео и аудио полностью декодируются без сохранения. Если длительность исходной записи известна, результат проверяется на преждевременное завершение с допуском 2 секунды или 1% длительности (что больше). На длинных записях проверка потребляет процессор и может занять дополнительное время. Дополнительно проверяются длительные участки почти чёрного изображения и тишины (не менее 20 секунд и 80% записи). Это только предупреждения: тишина или чёрный экран могут быть нормальными. Проверка не доказывает корректность начала, содержимого или синхронизации: просмотрите и прослушайте результат. Файлы, созданные до обновления, автоматически не проверяются.

Веб-интерфейс показывает свободное место для каталога результатов и состояния. Временные файлы контейнера могут находиться на другом разделе: его отображение работает только если вручную указан фактический путь `container_storage` в `state/operations.json` (см. ниже); иначе показано «неизвестно». При менее чем 1 ГиБ на любом известном разделе запрашивается подтверждение. Это предупреждение, не оценка требуемого размера: временный MP4 и копия результата могут одновременно занимать место на разных разделах.

Если запись состояния не удаётся, очередь приостанавливается и показывает ошибку, пока запись на диск снова не станет возможна; новые конвертации в это время не запускаются. Контроль ожидания: подготовка — до 10 минут; отсутствие прироста числа кадров FFmpeg при захвате — до 2 минут; общий лимит — два времени записи плюс 2 минуты, но не менее длительности плюс 2 минуты. Повторяющиеся записи в файле прогресса сами по себе не считаются движением кадров. Если после минуты работы число обработанных кадров отстаёт от реального времени более чем на 30 секунд и запись ещё не закончилась, задание останавливается с подсказкой: уменьшить разрешение или FPS, выбрать H.264 и быстрый пресет либо снизить число параллельных заданий. Эта эвристика не гарантирует корректность содержимого. При зависании возможны повторы, при перегрузке — нет; если остановку контейнера подтвердить нельзя, очередь не запускает следующее задание. Старые задания без сохранённых настроек используют оригинальный FFmpeg-скрипт без файла прогресса, для них действует общий лимит. Пороги ожидания можно изменить в systemd-окружении сервиса: `BBB_MP4_PREPARE_TIMEOUT` и `BBB_MP4_STALL_TIMEOUT` в секундах, `BBB_MP4_CAPTURE_TIMEOUT_FACTOR` и `BBB_MP4_CAPTURE_TIMEOUT_GRACE` для общего лимита.

### Резервные копии и уведомления (необязательно)

По умолчанию они выключены: необходимо отдельно указать хранилище и/или SMTP. На VM создайте `state/operations.json` от имени пользователя сервиса, задайте права `chmod 600 state/operations.json`. Пример — замените значения локально, **не отправляйте пароли в чат и не добавляйте файл в Git**:

```json
{
  "backup_dir": "/mnt/bbb-backup",
  "container_storage": "/фактический/путь/хранилища/контейнера",
  "smtp": {
    "host": "smtp.example.com", "port": 465, "mode": "ssl",
    "from": "bbb@example.com", "to": "admin@example.com",
    "username": "логин", "password": "пароль"
  }
}
```

Неиспользуемые ключи можно удалить. Для SMTP доступны `ssl` и `starttls`; при STARTTLS обычно используется порт 587. Настройки читаются при выполнении, перезапуск не обязателен. Сервис отправляет письмо при готовности или окончательной ошибке, без URL и журналов. Отправка выполняется в фоне и является best-effort: очередь писем не сохраняется при перезапуске, а принятие SMTP-сервером не гарантирует доставку адресату. Проверяйте статус в интерфейсе.

`backup_dir` должен быть **точкой монтирования** доступного пользователю сервиса внешнего хранилища на другой файловой системе, чем результаты и состояние; отсутствие монтирования или совпадение файловых систем считается ошибкой. Убедитесь отдельно, что это физически отдельный диск или удалённое хранилище. После завершения задания и при запуске сервиса копируются готовые MP4, список заданий, настройки, превью и digest образа в `backup_dir/bbb-mp4-simple/`. Можно запустить копирование кнопкой в интерфейсе. Каждый файл сначала копируется во временный и затем заменяется; предыдущий бэкап остаётся, если новая копия не удалась. Удаление или пересоздание локального файла не удаляет бэкап. Снимок *не является транзакционным архивом*: при восстановлении сверьте файлы и статусы вручную. Файл `operations.json` с паролями не копируется; резервируйте и восстанавливайте его отдельно безопасным способом. Бэкап содержит ссылки и журналы, поэтому ограничьте доступ к хранилищу. Статус виден в интерфейсе; проверяйте возможность восстановления и свободное место.

Для заданий с настройками прогресс приблизительно рассчитывается по числу кадров FFmpeg и выбранному FPS, а оставшееся время — по наблюдаемой средней скорости. Это не проверка содержимого и синхронизации. Для старых заданий без файла прогресса сохраняется оценка по времени с начала захвата. Пока оригинальный конвертер не определил длительность и не начал захват, время и прогресс неизвестны; на этапах финализации и проверки оставшееся время не оценивается. Причина сбоя и последние сообщения доступны в кнопке «Журнал» строки задания. Общий журнал сервиса:

```bash
journalctl -u bbb-mp4-web -n 100 --no-pager
```

**Безопасность:** входа по паролю и HTTPS нет. Любой, кто получит доступ к интерфейсу, сможет запускать и останавливать конвертацию, просматривать превью и скачивать или удалять файлы. Сервис слушает все интерфейсы на порту 8080 и принимает соединения только с IPv4-адресов RFC 1918 и localhost. Дополнительно ограничьте доступ сетевым экраном VM/Proxmox только доверенной подсетью; не публикуйте сервис в интернете и не размещайте его за публичным прокси. Ссылки на скачивание работают только там, где доступен адрес VM.

## Конвертация из командной строки

```bash
./convert.sh "https://vks.vsesem.ru/playback/presentation/2.3/f678f4a23ecaf2ac77135e744f2c9da8764c32dd-1793270594439"
```

Команда принимает один полный HTTP(S) playback URL формата, поддерживаемого оригиналом: `/playback/presentation/2.3/<40 строчных букв или цифр>-<13 цифр>`. Query string и fragment передаются без изменений. По умолчанию результат находится в `recordings/<meeting_id>.mp4` на VM, а не на сервере BBB. Скрипт работает в переднем плане до завершения контейнера. Контейнер работает с правами по умолчанию оригинального образа, поэтому созданные им файлы могут принадлежать root.

Конвертация использует оригинальный образ Chrome/Xvfb/FFmpeg. В контейнер подключается адаптированный сценарий браузера `bbb-mp4.js`; для заданий веб-интерфейса также подключается адаптированный скрипт FFmpeg `ffmpeg-cmd.sh` (лицензия оригинала — `LICENSE.upstream`); требования к странице playback и ограничения оригинального конвертера сохраняются. Никаких изменений на сервере BBB или в post_publish не производится.
